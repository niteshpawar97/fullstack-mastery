## Step 3: Database Layer — `db/`

**`MeterReadingDao.java`** (Day 5):
```java
package com.example.smartmeter.db;

import androidx.lifecycle.LiveData;
import androidx.room.*;
import com.example.smartmeter.model.MeterReadingEntity;
import java.util.List;

@Dao
public interface MeterReadingDao {
    @Insert
    long insert(MeterReadingEntity reading); // return type long — neeche wajah dekho

    @Update
    void update(MeterReadingEntity reading);

    @Query("SELECT * FROM meter_readings WHERE meter_id = :meterId ORDER BY timestamp DESC")
    LiveData<List<MeterReadingEntity>> getReadingsForMeter(String meterId);

    @Query("SELECT * FROM meter_readings WHERE sync_status = :status")
    List<MeterReadingEntity> getReadingsByStatus(String status);
}
```

> **🧠 Theory — `insert()` `void` Nahi, `long` Kyun Return Karta Hai:** `@PrimaryKey(autoGenerate = true)` wala `id` field database khud generate karta hai insert ke time — Java object banate waqt tumhe pata hi nahi hota naya row ka `id` kya banega. Agar `insert()` ko `void` rakho, to jo `entity` object insert kiya tha uska `.id` field **hamesha `0` hi rahega** (Room usse khud-ba-khud wapas fill nahi karta). Iska real nuksan tab dikhta hai jab **wahi entity object** turant baad `@Update` me use karo (jaise `attemptSync` me hota hai) — `UPDATE ... WHERE id = 0` kisi row ko match hi nahi karega, chahe network call kitna bhi successful kyun na ho, status kabhi **PENDING se aage badhega hi nahi**, bina kisi error/crash ke (silent failure — sabse dangerous kism ka bug). Isiliye `insert()` ko `long` return karwate hain, aur turant `entity.id = (int) dao.insert(entity)` se **wahi generated id wapas entity me daal dete hain**, taaki baad ka `dao.update(entity)` sahi row dhoondh sake.

> **🧠 Theory — `getReadingsForMeter` `LiveData` Kyun Return Karta Hai:** Room by default **kisi bhi database query ko main thread pe chalne hi nahi deta** (crash: `Cannot access database on the main thread`) — UI freeze hone se bachane ke liye. `getReadingsByStatus` (upar) plain `List` return karta hai kyunki wo hamesha `MeterRepository` ke andar `executor.execute()` ke through background thread pe call hoti hai. Lekin `getReadingsForMeter` ko `DashboardActivity` seedha `onCreate()` (main thread) se chahiye hoti hai — isiliye ye `LiveData<List<...>>` return karti hai: Room khud iska query background thread pe chalata hai, aur result LiveData ke through **safely main thread pe** wapas deta hai. Query ka type (`List` vs `LiveData<List>`) hi batata hai wo kahan se call hogi.

**`AppDatabase.java`** (Day 5 — singleton pattern):
```java
package com.example.smartmeter.db;

import android.content.Context;
import androidx.room.Database;
import androidx.room.Room;
import androidx.room.RoomDatabase;
import com.example.smartmeter.model.MeterReadingEntity;

@Database(entities = {MeterReadingEntity.class}, version = 1)
public abstract class AppDatabase extends RoomDatabase {
    public abstract MeterReadingDao meterReadingDao();

    private static volatile AppDatabase INSTANCE;

    public static AppDatabase getInstance(Context context) {
        if (INSTANCE == null) {
            synchronized (AppDatabase.class) {
                if (INSTANCE == null) {
                    INSTANCE = Room.databaseBuilder(context.getApplicationContext(),
                                    AppDatabase.class, "meter_database")
                            .build();
                }
            }
        }
        return INSTANCE;
    }
}
```

**`TokenManager.java`** (Day 5 — wraps EncryptedSharedPreferences):
```java
package com.example.smartmeter.util;

import android.content.Context;
import android.content.SharedPreferences;
import androidx.security.crypto.EncryptedSharedPreferences;
import androidx.security.crypto.MasterKey;
import java.security.GeneralSecurityException;
import java.io.IOException;

public class TokenManager {
    private final SharedPreferences prefs;

    public TokenManager(Context context) {
        try {
            MasterKey masterKey = new MasterKey.Builder(context)
                    .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
                    .build();
            prefs = EncryptedSharedPreferences.create(
                    context, "secure_prefs", masterKey,
                    EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
                    EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
            );
        } catch (GeneralSecurityException | IOException e) {
            throw new RuntimeException("Secure storage init failed", e);
        }
    }

    public void saveToken(String token, long expiresAt) {
        prefs.edit().putString("jwt_token", token).putLong("expires_at", expiresAt).apply();
    }

    public String getToken() {
        return prefs.getString("jwt_token", null);
    }

    public boolean isLoggedIn() {
        String token = getToken();
        long expiresAt = prefs.getLong("expires_at", 0);
        return token != null && System.currentTimeMillis() < expiresAt;
    }

    public void clear() {
        prefs.edit().clear().apply();
    }
}
```

**`NetworkUtils.java`** (Day 6):
```java
package com.example.smartmeter.util;

import android.content.Context;
import android.net.ConnectivityManager;
import android.net.Network;
import android.net.NetworkCapabilities;

public class NetworkUtils {
    public static boolean isOnline(Context context) {
        ConnectivityManager cm = (ConnectivityManager)
                context.getSystemService(Context.CONNECTIVITY_SERVICE);
        Network network = cm.getActiveNetwork();
        if (network == null) return false;
        NetworkCapabilities capabilities = cm.getNetworkCapabilities(network);
        return capabilities != null &&
               (capabilities.hasTransport(NetworkCapabilities.TRANSPORT_WIFI) ||
                capabilities.hasTransport(NetworkCapabilities.TRANSPORT_CELLULAR));
    }
}
```

## Step 5: API Layer — `api/`

**`AuthInterceptor.java`** (Day 4+5 — auto-attaches JWT):
```java
package com.example.smartmeter.api;

import androidx.annotation.NonNull;
import com.example.smartmeter.util.TokenManager;
import java.io.IOException;
import okhttp3.Interceptor;
import okhttp3.Request;
import okhttp3.Response;

public class AuthInterceptor implements Interceptor {
    private final TokenManager tokenManager;

    public AuthInterceptor(TokenManager tokenManager) {
        this.tokenManager = tokenManager;
    }

    @NonNull
    @Override
    public Response intercept(@NonNull Chain chain) throws IOException {
        Request original = chain.request();
        String token = tokenManager.getToken();

        if (token == null) return chain.proceed(original);

        Request authorized = original.newBuilder()
                .header("Authorization", "Bearer " + token)
                .build();
        return chain.proceed(authorized);
    }
}
```

**`RetrofitClient.java`** (Day 4 — OkHttp + Interceptor wired together):
```java
package com.example.smartmeter.api;

import android.content.Context;
import com.example.smartmeter.util.TokenManager;
import okhttp3.OkHttpClient;
import okhttp3.logging.HttpLoggingInterceptor;
import retrofit2.Retrofit;
import retrofit2.converter.gson.GsonConverterFactory;
import java.util.concurrent.TimeUnit;

public class RetrofitClient {
    private static Retrofit retrofit;
    private static final String BASE_URL = "https://api.smartmeter.com/";

    public static Retrofit getInstance(Context context) {
        if (retrofit == null) {
            HttpLoggingInterceptor logging = new HttpLoggingInterceptor();
            logging.setLevel(HttpLoggingInterceptor.Level.BODY);

            OkHttpClient client = new OkHttpClient.Builder()
                    .addInterceptor(new AuthInterceptor(new TokenManager(context.getApplicationContext())))
                    .addInterceptor(logging)
                    .connectTimeout(30, TimeUnit.SECONDS)
                    .readTimeout(30, TimeUnit.SECONDS)
                    .build();

            retrofit = new Retrofit.Builder()
                    .baseUrl(BASE_URL)
                    .client(client)
                    .addConverterFactory(GsonConverterFactory.create())
                    .build();
        }
        return retrofit;
    }
}
```

## Step 6: Repository Layer — `repository/`

**`AuthRepository.java`** (Day 5):
```java
package com.example.smartmeter.repository;

import android.content.Context;
import com.example.smartmeter.api.*;
import com.example.smartmeter.model.*;
import com.example.smartmeter.util.TokenManager;
import retrofit2.Call;
import retrofit2.Callback;
import retrofit2.Response;

public class AuthRepository {
    private final AuthApiService api;
    private final TokenManager tokenManager;

    public AuthRepository(Context context) {
        api = RetrofitClient.getInstance(context).create(AuthApiService.class);
        tokenManager = new TokenManager(context.getApplicationContext());
    }

    public void login(String email, String password, AuthCallback callback) {
        api.login(new LoginRequest(email, password)).enqueue(new Callback<LoginResponse>() {
            @Override
            public void onResponse(Call<LoginResponse> call, Response<LoginResponse> response) {
                if (response.isSuccessful() && response.body() != null) {
                    tokenManager.saveToken(response.body().token, response.body().expiresAt);
                    callback.onSuccess();
                } else {
                    callback.onError("Invalid credentials");
                }
            }
            @Override
            public void onFailure(Call<LoginResponse> call, Throwable t) {
                callback.onError("Network error: " + t.getMessage());
            }
        });
    }

    public boolean isLoggedIn() {
        return tokenManager.isLoggedIn();
    }

    public void logout() {
        tokenManager.clear();
    }

    public interface AuthCallback {
        void onSuccess();
        void onError(String message);
    }
}
```

**`MeterRepository.java`** (Day 6 — the offline-first core):
```java
package com.example.smartmeter.repository;

import android.content.Context;
import androidx.lifecycle.LiveData;
import com.example.smartmeter.api.*;
import com.example.smartmeter.db.*;
import com.example.smartmeter.model.*;
import com.example.smartmeter.util.NetworkUtils;
import com.example.smartmeter.util.SyncStatus;
import retrofit2.Call;
import retrofit2.Callback;
import retrofit2.Response;
import java.util.UUID;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class MeterRepository {
    private final MeterApiService api;
    private final MeterReadingDao dao;
    private final Context appContext;
    private final ExecutorService executor = Executors.newSingleThreadExecutor();

    public MeterRepository(Context context) {
        appContext = context.getApplicationContext();
        api = RetrofitClient.getInstance(context).create(MeterApiService.class);
        dao = AppDatabase.getInstance(context).meterReadingDao();
    }

    public void saveReading(String meterId, double reading) {
        MeterReadingEntity entity = new MeterReadingEntity();
        entity.clientUuid = UUID.randomUUID().toString();
        entity.meterId = meterId;
        entity.reading = reading;
        entity.timestamp = System.currentTimeMillis();
        entity.syncStatus = SyncStatus.PENDING;

        executor.execute(() -> {
            entity.id = (int) dao.insert(entity);
            if (NetworkUtils.isOnline(appContext)) {
                attemptSync(entity);
            }
        });
    }

    private void attemptSync(MeterReadingEntity entity) {
        MeterReadingRequest request = new MeterReadingRequest(
                entity.clientUuid, entity.meterId, entity.reading, entity.timestamp);

        api.submitReading(request).enqueue(new Callback<MeterReadingResponse>() {
            @Override
            public void onResponse(Call<MeterReadingResponse> call, Response<MeterReadingResponse> response) {
                entity.syncStatus = response.isSuccessful() ? SyncStatus.SYNCED : SyncStatus.FAILED;
                executor.execute(() -> dao.update(entity));
            }
            @Override
            public void onFailure(Call<MeterReadingResponse> call, Throwable t) {
                entity.syncStatus = SyncStatus.FAILED;
                executor.execute(() -> dao.update(entity));
            }
        });
    }

    public LiveData<java.util.List<MeterReadingEntity>> getReadingsForMeter(String meterId) {
        return dao.getReadingsForMeter(meterId);
    }

    public void syncAllPending() {
        executor.execute(() -> {
            for (MeterReadingEntity e : dao.getReadingsByStatus(SyncStatus.PENDING)) attemptSync(e);
            for (MeterReadingEntity e : dao.getReadingsByStatus(SyncStatus.FAILED)) attemptSync(e);
        });
    }
}
```

> **Yaad Rakho:** `getReadingsForMeter` yahan Repository se seedha DAO ka `LiveData` result pass-through kar deta hai — koi extra threading code Repository me likhne ki zaroorat nahi, Room khud background query handle karta hai (Day 7 ka `LiveData` pattern yahan extend ho raha hai).

```java
package com.example.smartmeter.ui;

import android.os.Bundle;
import androidx.appcompat.app.AppCompatActivity;
import androidx.lifecycle.ViewModelProvider;
import androidx.recyclerview.widget.LinearLayoutManager;
import androidx.work.*;
import com.example.smartmeter.databinding.ActivityDashboardBinding;
import com.example.smartmeter.repository.MeterRepository;
import com.example.smartmeter.viewmodel.*;
import com.example.smartmeter.worker.SyncWorker;
import java.util.concurrent.TimeUnit;

public class DashboardActivity extends AppCompatActivity {
    private ActivityDashboardBinding binding;
    private MeterViewModel viewModel;
    private static final String METER_ID = "MTR-001";

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        binding = ActivityDashboardBinding.inflate(getLayoutInflater());
        setContentView(binding.getRoot());

        MeterRepository repository = new MeterRepository(getApplicationContext());
        viewModel = new ViewModelProvider(this, new MeterViewModelFactory(repository))
                .get(MeterViewModel.class);

        MeterReadingAdapter adapter = new MeterReadingAdapter(new java.util.ArrayList<>());
        binding.recyclerView.setLayoutManager(new LinearLayoutManager(this));
        binding.recyclerView.setAdapter(adapter);

        // LiveData ka Room query background thread pe khud chalti hai, result yahan main thread pe aata hai
        viewModel.getReadings(METER_ID).observe(this, adapter::updateReadings);

        binding.btnSaveReading.setOnClickListener(v -> {
            String text = binding.etReading.getText().toString();
            if (text.isEmpty()) return;
            viewModel.saveReading(METER_ID, Double.parseDouble(text));
            binding.etReading.setText("");
            // list save hote hi khud refresh ho jaati hai — LiveData observer automatically fire hota hai
        });

        schedulePeriodicSync();
    }

    private void schedulePeriodicSync() {
        Constraints constraints = new Constraints.Builder()
                .setRequiredNetworkType(NetworkType.CONNECTED)
                .build();
        PeriodicWorkRequest syncRequest = new PeriodicWorkRequest.Builder(SyncWorker.class, 15, TimeUnit.MINUTES)
                .setConstraints(constraints)
                .build();
        WorkManager.getInstance(this)
                .enqueueUniquePeriodicWork("meter_sync", ExistingPeriodicWorkPolicy.KEEP, syncRequest);
    }
}
```

### Common Assembly Errors

| Error | Fix |
|-------|-----|
| `Cannot resolve symbol 'ActivityLoginBinding'` | View Binding `build.gradle.kts` me `viewBinding = true` set hai ya nahi check karo, phir **Build → Rebuild Project** |
| `Room cannot verify the data integrity` | App uninstall karke dobara install karo (schema version mismatch — dev me normal hai) |
| `NetworkOnMainThreadException` | Kahin `.execute()` (Retrofit sync call) ya Room query bina `executor.execute()` ke main thread pe chal rahi hai |
| `IllegalStateException: Cannot access database on the main thread` | Koi Room DAO method jo plain `List` (LiveData nahi) return karta hai, `onCreate()`/UI code se seedha call ho raha hai — ya to `executor.execute()` ke andar call karo, ya `LiveData<List<...>>` return type use karo (jaise `getReadingsForMeter` isi guide me karta hai) |
| Reading `SYNCED` kabhi nahi hoti (hamesha `PENDING` rehti hai, bina error ke) | `@Insert` DAO method `void` return kar raha hai — us entity ka `.id` `0` hi rehta hai, isliye baad ka `dao.update(entity)` `WHERE id = 0` se koi row match nahi karta (silent no-op). `insert()` ko `long` return karo aur `entity.id = (int) dao.insert(entity)` karo |
| `IllegalStateException: WorkManager is not initialized` | `androidx.work:work-runtime` dependency check karo, Gradle sync dobara karo |
| App crash on `AppCompatActivity` not found | `androidx.appcompat:appcompat` dependency missing — Step 0 dubara check karo |

## 🗺️ Poora App Ka Flow Chart — Revision Guide

Ab jab poora project ban chuka hai, ye section **padhne ke liye** hai — taaki "kaunsi file kya kaam karti hai, aur kis din wala concept hai" ek nazar me clear ho jaaye. Jab bhi confuse ho, yahan wapas aa jaana.

### 1. Architecture — Data Kis Tarah Layer-By-Layer Flow Karta Hai

```
[UI Layer — ui/]
   LoginActivity, DashboardActivity, MeterReadingAdapter
        │
        │  observe LiveData (data dikhane ke liye) / call (action ke liye)
        ▼
[ViewModel Layer — viewmodel/]
   MeterViewModel, MeterViewModelFactory
        │
        │  call
        ▼
[Repository Layer — repository/]
   AuthRepository, MeterRepository
   (yahi decide karta hai: "Room se padhna hai ya API se?")
        │
        ├──────────────────────────────┐
        ▼                                ▼
[db/ — Room]                    [api/ — Retrofit]
   AppDatabase, DAO                RetrofitClient, AuthInterceptor,
   (local, offline data)           AuthApiService, MeterApiService
                                        │
                                        │  HTTP/JSON
                                        ▼
                                [PHP Backend — Day 9]
                                   login.php, register.php,
                                   get_readings.php, submit_reading.php
                                        │
                                        │  PDO (prepared statements)
                                        ▼
                                [MySQL Database]
                                   users, meter_readings
```

> **Yaad Rakho:** Har layer sirf apne **seedhe neeche** wale layer ko jaanta hai — `ui/` ko kabhi pata nahi hota Retrofit ya Room kaise kaam karte hain, wo sirf ViewModel se baat karta hai. Ye MVVM + Repository pattern ka poora point hai (Day 7): layers independently badal sakte ho (jaise Room ki jagah koi doosra local DB use kar lo) bina baaki layers ko chhue.

### 2. Flow 1 — Login Se Dashboard Tak

1. User email/password type karke **"Login"** dabata hai.
2. `LoginActivity` → `AuthRepository.login(email, password, callback)` call karta hai.
3. `AuthRepository` → `AuthApiService.login()` → Retrofit se `POST /login.php` jaata hai.
4. PHP side: `SELECT user WHERE email = ?` → `password_verify(password, hash)` check hota hai.
5. **Agar galat:** `401` + `{"error": "Invalid credentials"}` wapas aata hai → `callback.onError()` → `LoginActivity` error text dikhata hai, user wahin ruka rehta hai.
6. **Agar sahi:** `generateJWT()` se token banta hai → `200` + `{token, expiresAt}` wapas aata hai → `AuthRepository` `TokenManager.saveToken()` se token `EncryptedSharedPreferences` me save karta hai → `callback.onSuccess()` → `startActivity(DashboardActivity)`.

> **Socho Aise:** `AuthRepository` yahan ek **beech ka aadmi** hai — `LoginActivity` ko pata hi nahi ki JWT kaise banta hai ya kahan store hota hai, wo bas "success ya error" sunta hai. Ye responsibility-separation hai (Day 1 ka Encapsulation, real project me).

### 3. Flow 2 — Reading Save + Offline Sync (Sabse Important Flow)

1. User number type karke **"Save Reading"** dabata hai.
2. `DashboardActivity` → `viewModel.saveReading(meterId, reading)` → `MeterRepository.saveReading()`.
3. Ek naya `MeterReadingEntity` banta hai: `clientUuid = UUID.randomUUID()`, `syncStatus = PENDING`.
4. Ye sab `executor.execute { ... }` ke andar (**background thread**, Day 6 ka threading theory) hota hai:
   - `dao.insert(entity)` — Room me `PENDING` status ke saath save, aur generated `id` wapas `entity` me aata hai (`long insert()`).
   - Room ki `LiveData` isi second **khud-ba-khud** `DashboardActivity` ko naya data bhej deti hai — UI turant "PENDING" dikhata hai, koi manual refresh call nahi lagi.
5. `NetworkUtils.isOnline()` check hota hai:
   - **Online hai:** `attemptSync(entity)` turant call hoti hai → `POST /submit_reading.php` (`AuthInterceptor` khud `Authorization: Bearer <token>` header laga deta hai) → PHP JWT verify karta hai, `client_uuid UNIQUE` check karta hai, insert/existing return karta hai → response aate hi `entity.syncStatus = SYNCED` (ya `FAILED`) → `dao.update(entity)` → `LiveData` phir se UI refresh kar deti hai.
   - **Offline hai:** kuch nahi hota, reading `PENDING` hi reh jaati hai.
6. **Safety net:** `WorkManager` ka `SyncWorker` har **15 minute** (jab bhi internet available ho) `syncAllPending()` chalata hai — jo bhi readings `PENDING`/`FAILED` hain, unke liye phir se step 5 ka "online" wala flow chalta hai.

> **Interview Trap:** "Agar app 3 baar crash ho jaaye submit karte waqt, kya server pe 3 duplicate readings ban jaayengi?" — **Nahi**, kyunki `client_uuid` client pe ek hi baar generate hota hai (step 3), aur server `client_uuid UNIQUE` constraint + pehle-check-karo logic (Day 9) se dobara aane pe **wahi purana record** wapas kar deta hai, naya insert nahi karta.

### 5. Interview Ke Liye Zaroori Comparisons

Code likhna ek cheez hai, interview me "X aur Y me kya farak hai, kab kaunsa use karoge" jaise sawaal ka **turant, confident** jawab dena bilkul alag skill hai. Ye poore course me jo bhi "do options me se ek chuna" — unka comparison ek jagah:

**A. Storage Options — SharedPreferences vs SQLite vs Room vs EncryptedSharedPreferences**

| | Kya Store Karta Hai | Query Support | Kab Use Karo | Is Course Me |
|---|---|---|---|---|
| `SharedPreferences` | Simple key-value (String/int/boolean) | Nahi — sirf key se ek value milti hai | Chhoti settings — theme, "onboarding dikha diya" flag | — |
| `EncryptedSharedPreferences` | Key-value, **AES-256 encrypted** | Nahi | Sensitive **chhota** data — JWT token, refresh token | Day 5 (`TokenManager`) |
| SQLite (raw) | Relational tables, raw SQL strings | Full SQL, par manual `Cursor` handling | Jab bahut fine-grained control chahiye, ya legacy code maintain karna ho | Day 5 (theory ke liye) |
| Room | SQLite ke **upar** type-safe layer | Full SQL, **compile-time verified** | Structured, list-wala, relational data — offline cache, history | Day 5, 6, 8 (`AppDatabase`) |

> **Interview Trap:** "JWT token store karne ke liye Room use kyun nahi kiya?" — Room **structured, queryable** data ke liye best hai (jaise readings ki list, jisme filter/sort chahiye). Ek akela token sirf key-value hai, usko poora table/schema banake store karna **over-engineering** hoga — `EncryptedSharedPreferences` isi ke liye bana hai. Sahi tool sahi kaam ke liye chunna hi is sawaal ka asli point hai.

**B. Explicit vs Implicit Intent**

| | Explicit Intent | Implicit Intent |
|---|---|---|
| Target kaise batate ho | Exact class naam deke (`DashboardActivity.class`) | Sirf **action** batake (`ACTION_VIEW`), system decide karta hai kaun handle karega |
| Example | `new Intent(this, DashboardActivity.class)` | `new Intent(Intent.ACTION_VIEW, Uri.parse(url))` |
| Kab use karo | Apni **hi app ke andar** ek screen se doosri pe jaana | **Doosri app** ko kaam sonpna — browser kholna, share karna, call lagana |
| Is course me | `LoginActivity` → `DashboardActivity` (Day 2, Day 8) | — (is capstone me nahi use hua, par Android me bahut common hai) |

**C. Serializable vs Parcelable**

| | Serializable | Parcelable |
|---|---|---|
| Kya hai | **Java** ka standard interface | **Android-specific** interface |
| Kaise kaam karta hai | Reflection use karta hai (object ko byte stream banata hai) | Manually, Android ke liye optimized code (auto-generate hota hai) |
| Performance | **Slow** | **Fast** — Android me isiliye preferred hai |
| Kab use | Quick prototyping, jab performance matter na kare | Production Android app — Intent me object pass karna ho to |

**D. Synchronous vs Asynchronous Network Calls (Retrofit)**

| | `.execute()` (Sync) | `.enqueue()` (Async) |
|---|---|---|
| Chalta kahan hai | **Jis bhi thread se call kiya** usi ko block kar deta hai | Background thread pe, result **callback** se wapas aata hai |
| Main thread pe use karo? | **Kabhi nahi** — `NetworkOnMainThreadException` crash | Hamesha — poore is course me yehi use hua (`enqueue()`) |
| Kyun | Network call me seconds lag sakte hain — UI thread block = **frozen app / ANR** | UI thread free rehta hai, app responsive rehti hai |

**E. Background Kaam: Thread vs AsyncTask vs ExecutorService vs WorkManager**

| | Kab Use Karo | Guarantee |
|---|---|---|
| Raw `Thread` | Bahut low-level control chahiye ho | Koi lifecycle-awareness nahi — memory leak ka risk |
| `AsyncTask` | **Mat use karo** — deprecated (API 30+) | — |
| `ExecutorService` | One-time background kaam, jab tak **app open hai** | App band (process kill) hote hi kaam ruk jaata hai |
| `WorkManager` | **Guaranteed** background kaam — app band ho, phone restart ho, phir bhi chalega | System-level guarantee, constraints support karta hai (network/battery) |
| Is course me | `ExecutorService` — Repository ke turant-turant DB writes (Day 6); `WorkManager` — periodic sync (Day 6) | — |

> **Yaad Rakho:** Ye ek progression hai — `Thread` sabse purana/manual, `AsyncTask` beech ka (ab deprecated), `ExecutorService` reliable one-time kaam ke liye, `WorkManager` sabse **guaranteed** hai. Interview me "in sab me farak batao" pooche to isi order me answer do — evolution ki tarah.

**F. MVC vs MVP vs MVVM**

| | Full Form | Core Idea | Is Course Me |
|---|---|---|---|
| MVC | Model-View-Controller | Controller View aur Model dono ko directly manage karta hai | — |
| MVP | Model-View-Presenter | Presenter UI logic handle karta hai, View se loosely coupled | — |
| MVVM | Model-View-ViewModel | ViewModel data **expose** karta hai (`LiveData`), View sirf **observe** karta hai — View ko pata hi nahi kaise data aaya | **Poora capstone isi pe bana hai** (Day 7, Day 8) |

> **Interview Trap:** "MVVM me ViewModel ko View ka reference kyun nahi rakhna chahiye?" — Kyunki agar ViewModel ke paas Activity/Fragment ka reference ho, aur screen rotate ho jaaye (Activity destroy-recreate hoti hai), to ViewModel purani, **dead** Activity ko pakड़े रहेगा — memory leak. Isi liye ViewModel sirf `LiveData` **expose** karta hai, View khud aake **observe** karta hai — direction hamesha View → ViewModel, kabhi ulta nahi.

**G. Abstract Class vs Interface (Java)**

| | Abstract Class | Interface |
|---|---|---|
| Multiple inheritance | Nahi (Java me ek class sirf ek hi extend kar sakti hai) | Haan (ek class multiple interfaces implement kar sakti hai) |
| State (fields) rakh sakta hai? | Haan | Nahi (sirf constants) |
| Is course me | `RoomDatabase` (Room ka base class jo `AppDatabase` extend karta hai) | `MeterReadingDao`, `AuthApiService`, `MeterApiService` (Day 4, Day 5 — sab `interface` hain) |

> **Socho Aise:** Interface batata hai "**kya** karna hai" (contract), abstract class dega "**kya** aur kuch **kaise**" (partial implementation). Retrofit ke API services interfaces isliye hain kyunki unka koi implementation hi nahi likhna — Retrofit khud runtime pe implementation generate kar deta hai.

### 6. Production Ke Liye Zaroori Cheezein — HTTPS, Certificates, ProGuard, Gradle Build Config

Ye woh cheezein hain jo "app chal rahi hai" aur "app **production-ready** hai" ke beech ka farak banati hain — interview me senior-level sawaal isi taraf jaate hain.

**A. HTTP vs HTTPS**

| | HTTP | HTTPS |
|---|---|---|
| Encryption | Nahi — data **plain text** me jaata hai | Haan — TLS/SSL se **encrypted** |
| Port | 80 | 443 |
| Certificate chahiye? | Nahi | Haan — ek trusted CA (Certificate Authority) se signed SSL certificate |
| Beech me koi padh sakta hai? | Haan — same WiFi pe koi bhi (jaise college/office network) data dekh sakta hai | Nahi — encrypted hai, sirf server aur client hi decrypt kar sakte hain |
| Is course me | Local dev (`10.0.2.2`, `usesCleartextTraffic="true"`) — Day 8 | Production (`askt.in` jaisa real host) — Day 9 |

> **Yaad Rakho:** `usesCleartextTraffic="true"` isiliye sirf **dev/testing** ke liye hai — production app kabhi plain HTTP pe live nahi honi chahiye. JWT token, password — sab kuch bina encryption ke jaa raha ho to koi bhi beech me baithi hui party (public WiFi, ISP) padh sakti hai.

**Theory — HTTPS Ke Peeche Kya Hota Hai (TLS Handshake, Short Version):**

1. App server se connect karta hai — server apna **SSL certificate** bhejta hai (isme server ki public key hoti hai, aur ek trusted CA — jaise Let's Encrypt — ka digital signature hota hai).
2. Android **khud verify** karta hai ki ye certificate kisi **trusted CA** ne sign kiya hai (phone/emulator me pehle se ek list hoti hai kaunse CA trust karne hain — "trust store").
3. Verify hone ke baad, dono taraf ek **symmetric session key** negotiate karte hain (asymmetric encryption sirf handshake ke liye, baaki poori conversation fast symmetric encryption se hoti hai).
4. Ab jitna bhi data jaaye (login, JWT, readings) — sab is session key se encrypted hai.

> **Interview Trap:** "Agar koi fake server tumhare app ka HTTPS traffic intercept karna chahe, kya ho sakta hai?" — Agar attacker **apna khud ka certificate** present kare (self-signed ya kisi doosri site ke liye), Android use **reject** kar dega kyunki wo trusted CA se match nahi karega — isko **Man-in-the-Middle (MITM) attack** kehte hain, aur HTTPS ka poora point hi ye hai ki normal setup me ye fail ho jaaye. Aur extra security chahiye ho (jaise banking apps) to **Certificate Pinning** use karte hain — app sirf ek **exact** certificate accept karta hai, kisi bhi trusted CA ka nahi (OkHttp me `CertificatePinner` se).

**B. ProGuard vs R8**

| | ProGuard | R8 |
|---|---|---|
| Kaun banata hai | Third-party tool (purana) | Google ka apna, **default** tool ab |
| Status | Legacy naam abhi bhi use hota hai (`proguard-rules.pro` file) | Android Gradle Plugin 3.4+ se **default** |
| Kaam | Code **shrink** + **obfuscate** + **optimize** | Same kaam, faster aur behtar optimized |

**Kya Karta Hai (teeno kaam alag-alag samjho):**

| Kaam | Matlab |
|---|---|
| **Shrink** | Jo code/resources use hi nahi ho rahe, unhe APK se **hata deta hai** (chhota APK size) |
| **Obfuscate** | Class/method/variable names ko **meaningless names** (`a`, `b`, `c`) me rename kar deta hai — reverse-engineer karna mushkil ho jaata hai |
| **Optimize** | Bytecode ko aur **efficient** bana deta hai (dead code paths remove, inlining, etc.) |

> **Interview Trap — Sabse Bada ProGuard Gotcha:** "App debug build me perfectly chalti hai, par release build (Play Store wali) me crash ya blank data aata hai — kyun?" Jawab: **Gson jaisi libraries reflection use karti hain** — JSON field `"meterId"` ko Java field `meterId` se **naam match karke** jodti hain. Agar `minifyEnabled true` hai bina sahi `-keep` rules ke, R8 `MeterReadingResponse.meterId` field ka naam badal ke `a.b` bana deta hai — ab Gson ko field mil hi nahi raha, silently `null` aata hai (crash nahi, bas data ghayab). Isiliye `proguard-rules.pro` me apne model classes ke liye ye zaroori hai:
> ```
> -keep class com.example.smartmeter.model.** { *; }
> ```
> Room entities is course me safe hain kyunki Room **annotation processing** (compile-time) use karta hai, reflection nahi — par network models (Gson se serialize/deserialize hone wale) ko hamesha `-keep` karo.

**C. Gradle Build Types — `debug` vs `release`**

| | `debug` | `release` |
|---|---|---|
| Signing | Automatic (Android Studio ki apni debug keystore) | Manual — apni khud ki keystore chahiye (`signingConfig`) — Play Store isi se pehchanta hai ki update **tumhara hi** hai |
| `minifyEnabled` | Aam taur pe `false` (fast build, poora debug info) | Aam taur pe `true` (R8 chalta hai — chhota, obfuscated APK) |
| Logging | Verbose (`HttpLoggingInterceptor` BODY level jaisa is course me) | Kam/bandh (production me raw request/response log karna security risk hai) |

**Practical Use — `buildConfigField` Se `BASE_URL` Automatically Switch Karna:**

Aaj tumne khud dekha — local XAMPP aur remote `askt.in` ke beech `BASE_URL` **manually** badalna pada har baar. Iska proper solution:

```kotlin
// app/build.gradle.kts
android {
    buildFeatures {
        buildConfig = true   // AGP 8+ me ye explicitly ON karna padta hai
    }
    buildTypes {
        debug {
            buildConfigField("String", "BASE_URL", "\"http://10.0.2.2/smartmeter-api/\"")
        }
        release {
            buildConfigField("String", "BASE_URL", "\"https://askt.in/smartmeter-api/\"")
            isMinifyEnabled = true
            proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
        }
    }
}
```

Phir `RetrofitClient.java` me hardcoded string ki jagah:

```java
private static final String BASE_URL = BuildConfig.BASE_URL;
```

Ab **Debug** run karoge to khud-ba-khud local URL use hoga, **Release** build banate hi khud-ba-khud production URL — kabhi bhi manually file edit karke bhool jaane (aur galti se galat URL production APK me chale jaane) ka risk khatam.

> **Socho Aise:** Ye bilkul waisa hi hai jaise Day 9 me `.env`/`config.php` alag rakha tha secrets ke liye — code aur **environment-specific config** ko alag rakhna hai, taaki ek hi codebase alag-alag jagah (dev/production) sahi tarike se chale bina manual edit ke.
