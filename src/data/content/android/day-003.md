## Block 1 — RecyclerView: Adapter + ViewHolder Pattern

### Kyun RecyclerView, `ListView` Nahi?

Purana `ListView` har item ke liye baar-baar naya view banata tha — scroll karte waqt lag hota tha. `RecyclerView` **views recycle** karta hai — jo item screen se bahar gaya, uska view naye item ke liye reuse ho jaata hai.

> **Socho Aise:** Ek bus me 10 seats hain, 1000 passengers aane wale hain. `ListView` = har passenger ke liye nayi seat banwana (bahut mehnga). `RecyclerView` = jab ek passenger utarta hai, uski seat turant agle passenger ko de dena — sirf 10 seats kaafi hain.

### 🧠 Theory: "Inflating" Ek View Itni Mehngi Kyun Hai

XML layout file ko actual on-screen View objects me convert karna (`inflate()`) ek **multi-step process** hai — XML parse karna, har tag ke liye Java object banana, attributes (padding, color, text) apply karna, sabko tree me arrange karna. Ye CPU-heavy kaam hai.

Ek list me agar 1000 items hain aur screen pe ek time pe sirf **10 dikhte** hain, to sirf **10-15 views** (thoda buffer ke saath) actually kabhi bante hain — RecyclerView unhi 10-15 views ko baar-baar reuse karta hai jaise-jaise scroll hota hai. Ye hi wajah hai ki RecyclerView 10,000 items wali list ko bhi utni hi smoothly handle karta hai jitna 10 items wali — inflate sirf ek baar (ya kabhi kabhi thoda zyada) hota hai, data-binding baar-baar (sasta).

```java
// 3. Adapter — data ko views se jodne wala pul
public class MeterReadingAdapter extends RecyclerView.Adapter<MeterReadingAdapter.ViewHolder> {
    private List<MeterReading> readings;

    public MeterReadingAdapter(List<MeterReading> readings) {
        this.readings = readings;
    }

    // ViewHolder — ek row ke views ko "hold" karta hai (baar-baar findViewById na karna pade)
    public static class ViewHolder extends RecyclerView.ViewHolder {
        TextView tvMeterId, tvReading, tvTimestamp;
        public ViewHolder(View itemView) {
            super(itemView);
            tvMeterId = itemView.findViewById(R.id.tvMeterId);
            tvReading = itemView.findViewById(R.id.tvReading);
            tvTimestamp = itemView.findViewById(R.id.tvTimestamp);
        }
    }

    @NonNull
    @Override
    public ViewHolder onCreateViewHolder(@NonNull ViewGroup parent, int viewType) {
        View view = LayoutInflater.from(parent.getContext())
                .inflate(R.layout.item_meter_reading, parent, false);
        return new ViewHolder(view);
    }

    @Override
    public void onBindViewHolder(@NonNull ViewHolder holder, int position) {
        MeterReading reading = readings.get(position);
        holder.tvMeterId.setText(reading.meterId);
        holder.tvReading.setText(reading.reading + " units");
        holder.tvTimestamp.setText(reading.timestamp);
    }

    @Override
    public int getItemCount() {
        return readings.size();
    }
}
```

**Activity me use karna:**

> **Yaad Rakho:** `RecyclerView` khud kuch nahi jaanta data ke baare me — `Adapter` hi decide karta hai kitne items hain (`getItemCount`), har item kaisa dikhega (`onBindViewHolder`), aur row ka layout kaisa banega (`onCreateViewHolder`).

## Block 2 — onCreateViewHolder, onBindViewHolder, getItemCount Deep Dive

| Method | Kab Chalta Hai | Kya Karta Hai |
|--------|----------------|----------------|
| `onCreateViewHolder()` | Sirf jab **naya** view chahiye hota hai (recycle nahi ho sakta) | XML row inflate karke `ViewHolder` banata hai |
| `onBindViewHolder()` | **Har baar** jab koi item screen pe dikhna hai | ViewHolder ke views me actual data set karta hai |
| `getItemCount()` | Jab bhi RecyclerView list ka size jaanna chahta hai | List ka total size return karta hai |

> **Socho Aise:** `onCreateViewHolder` = ek naya khaali plate banana (mehnga kaam — kabhi kabhi hota hai). `onBindViewHolder` = plate me khana serve karna (sasta kaam — baar-baar hota hai, jab bhi plate reuse ho).

```java
@Override
public void onBindViewHolder(@NonNull ViewHolder holder, int position) {
    // YAHAN heavy work mat karo — ye scroll karte waqt baar-baar chalta hai
    MeterReading reading = readings.get(position);
    holder.tvMeterId.setText(reading.meterId);   // fast, direct assignment
}
```

> **Warning:** `onBindViewHolder()` ke andar network call, database query, ya bitmap decoding **kabhi mat karo** — ye har scroll frame pe chal sakta hai aur UI stutter/lag karegi.

## Block 3 — Multiple Lists (Multiple View Types)

Ek RecyclerView me alag-alag type ke items dikhane hote hain — jaise "Normal Reading" aur "Alert Reading" alag dikhein.

```java
public class MixedAdapter extends RecyclerView.Adapter<RecyclerView.ViewHolder> {
    private static final int TYPE_NORMAL = 0;
    private static final int TYPE_ALERT = 1;

    @Override
    public int getItemViewType(int position) {
        MeterReading r = readings.get(position);
        return r.reading > 500 ? TYPE_ALERT : TYPE_NORMAL;   // high reading = alert
    }

    @NonNull
    @Override
    public RecyclerView.ViewHolder onCreateViewHolder(@NonNull ViewGroup parent, int viewType) {
        if (viewType == TYPE_ALERT) {
            View v = LayoutInflater.from(parent.getContext())
                    .inflate(R.layout.item_alert_reading, parent, false);
            return new AlertViewHolder(v);
        } else {
            View v = LayoutInflater.from(parent.getContext())
                    .inflate(R.layout.item_meter_reading, parent, false);
            return new NormalViewHolder(v);
        }
    }

    @Override
    public void onBindViewHolder(@NonNull RecyclerView.ViewHolder holder, int position) {
        if (holder instanceof AlertViewHolder) {
            ((AlertViewHolder) holder).bind(readings.get(position));
        } else {
            ((NormalViewHolder) holder).bind(readings.get(position));
        }
    }
}
```

> **Yaad Rakho:** `getItemViewType()` decide karta hai kaunsa layout use hoga. Har view type ka apna `ViewHolder` subclass hota hai (polymorphism — kal ka topic yahan kaam aa raha hai!).

## Block 4 — RecyclerView Performance

### Common Performance Mistakes

1. **`onBindViewHolder` me `findViewById`** — ViewHolder pattern ka poora point ye avoid karna hai. Views sirf ek baar `onCreateViewHolder` me find karo.
2. **Heavy objects baar-baar banana** — jaise `new SimpleDateFormat()` har bind pe. Ise class-level (static/final) banao.
3. **`notifyDataSetChanged()` bar-bar full list ke liye** — poori list refresh karta hai, slow hai. Specific changes ke liye `notifyItemInserted()`, `notifyItemChanged()`, `notifyItemRemoved()` use karo.
4. **`setHasFixedSize(true)` na lagana** — agar list ka size change nahi hota (layout ke hisab se), ye RecyclerView ko unnecessary layout calculations se bachata hai.

```java
// Poori list refresh (slow, avoid jab possible ho)
notifyDataSetChanged();

// Specific item change (fast, preferred)
readings.add(newReading);
adapter.notifyItemInserted(readings.size() - 1);

readings.remove(position);
adapter.notifyItemRemoved(position);
```

> **Socho Aise:** `notifyDataSetChanged()` = poore ghar ki safai (sab kuch check karo). `notifyItemInserted()` = sirf ek naya kamra add hua, sirf wahi paint karo.

### DiffUtil — Smart Comparison

```java
DiffUtil.DiffResult result = DiffUtil.calculateDiff(new DiffUtil.Callback() {
    @Override public int getOldListSize() { return oldList.size(); }
    @Override public int getNewListSize() { return newList.size(); }
    @Override public boolean areItemsTheSame(int oldPos, int newPos) {
        return oldList.get(oldPos).meterId.equals(newList.get(newPos).meterId);
    }
    @Override public boolean areContentsTheSame(int oldPos, int newPos) {
        return oldList.get(oldPos).reading == newList.get(newPos).reading;
    }
});
result.dispatchUpdatesTo(adapter);
```

> **Tip:** `DiffUtil` purani aur nayi list compare karke sirf wahi items update karta hai jo actually badle hain — large datasets (jaise 6-monthly meter history) ke liye essential hai.

## Block 5 — Fragment: Kya Hai, Kyun Chahiye

`Fragment` ek **reusable UI piece** hai jo ek Activity ke andar rahta hai — apna khud ka layout aur lifecycle rakhta hai.

> **Socho Aise:** Activity ek ghar hai, Fragment ek kamra hai. Ghar (Activity) ke andar tum kamre (Fragments) badal sakte ho bina poora ghar (Activity) dobara banaye — tab switching (List / Details / Settings) is wajah se fast aur smooth hoti hai.

```java
public class ReadingListFragment extends Fragment {
    @Override
    public View onCreateView(LayoutInflater inflater, ViewGroup container, Bundle savedInstanceState) {
        return inflater.inflate(R.layout.fragment_reading_list, container, false);
    }

    @Override
    public void onViewCreated(View view, Bundle savedInstanceState) {
        super.onViewCreated(view, savedInstanceState);
        RecyclerView rv = view.findViewById(R.id.recyclerView);
        rv.setLayoutManager(new LinearLayoutManager(requireContext()));
        rv.setAdapter(new MeterReadingAdapter(getReadings()));
    }
}
```

### Activity Me Fragment Host Karna

```xml
<!-- activity_main.xml -->
<FrameLayout
    android:id="@+id/fragmentContainer"
    android:layout_width="match_parent"
    android:layout_height="match_parent" />
```

```java
getSupportFragmentManager()
    .beginTransaction()
    .replace(R.id.fragmentContainer, new ReadingListFragment())
    .commit();
```

> **Yaad Rakho:** Fragment ko akela "chalaya" nahi ja sakta — usko hamesha ek Activity **host** karti hai `FragmentManager` ke through.

## Block 6 — Fragment Lifecycle

Fragment lifecycle Activity se **zyada steps** rakhta hai kyunki iski apni state aur Activity ki state dono manage honi hoti hai:

```
onAttach() → onCreate() → onCreateView() → onViewCreated()
→ onStart() → onResume()
→ onPause() → onStop() → onDestroyView() → onDestroy() → onDetach()
```

| Callback | Kya Karo Yahan |
|----------|----------------|
| `onAttach()` | Fragment Activity se judta hai — Context milta hai |
| `onCreateView()` | XML layout inflate karo, view return karo |
| `onViewCreated()` | Views ke saath kaam shuru karo (RecyclerView setup, click listeners) |
| `onDestroyView()` | View references clear karo (memory leak se bachne ke liye) |
| `onDetach()` | Fragment Activity se poori tarah alag ho gaya |

> **Warning:** `onDestroyView()` me View Binding reference ko `null` set karna best practice hai — Fragment ka view destroy ho sakta hai jabki Fragment khud zinda rahe (jaise back stack me), aur purana view reference memory leak karega.

```java
public class ReadingListFragment extends Fragment {
    private FragmentReadingListBinding binding;

    @Override
    public View onCreateView(LayoutInflater inflater, ViewGroup container, Bundle savedInstanceState) {
        binding = FragmentReadingListBinding.inflate(inflater, container, false);
        return binding.getRoot();
    }

    @Override
    public void onDestroyView() {
        super.onDestroyView();
        binding = null;   // memory leak prevention
    }
}
```

## Block 7 — Activity vs Fragment

| | Activity | Fragment |
|---|---|---|
| Independent? | Haan, khud chal sakti hai | Nahi, hamesha ek Activity chahiye |
| Lifecycle | Simpler (6 callbacks) | Complex (Activity ke lifecycle se juda) |
| Reusability | Kam — poori screen hai | Zyada — same Fragment alag Activities me use ho sakta hai |
| Navigation | `startActivity()` — nayi screen, back stack me nayi entry | `FragmentManager` — same Activity ke andar swap |
| Best for | App ka entry point, poori tarah alag flows (Login vs Main) | Tab switching, list-detail (master-detail), reusable UI sections |

> **Socho Aise:** Agar screens ke beech **poora context switch** ho raha hai (jaise Login se Dashboard) → Activity. Agar same screen ke andar **content badal raha hai** (jaise bottom nav tabs) → Fragment.

### Mini Project: Meter Reading List App

**Goal:** Ek Fragment jo RecyclerView me meter readings dikhaye, item click pe ek doosre Fragment me detail dikhaye.

```java
public class ReadingListFragment extends Fragment {
    private List<MeterReading> readings;

    @Override
    public void onViewCreated(View view, Bundle savedInstanceState) {
        super.onViewCreated(view, savedInstanceState);

        readings = new ArrayList<>();
        readings.add(new MeterReading("MTR-001", 245.5, "2026-08-20 09:00"));
        readings.add(new MeterReading("MTR-002", 189.2, "2026-08-20 09:05"));
        readings.add(new MeterReading("MTR-003", 601.0, "2026-08-20 09:10"));

        RecyclerView rv = view.findViewById(R.id.recyclerView);
        rv.setLayoutManager(new LinearLayoutManager(requireContext()));

        MeterReadingAdapter adapter = new MeterReadingAdapter(readings, meterId -> {
            // item click callback — detail fragment pe navigate karo
            Bundle args = new Bundle();
            args.putString("METER_ID", meterId);
            ReadingDetailFragment detail = new ReadingDetailFragment();
            detail.setArguments(args);
            getParentFragmentManager().beginTransaction()
                    .replace(R.id.fragmentContainer, detail)
                    .addToBackStack(null)
                    .commit();
        });
        rv.setAdapter(adapter);
    }
}
```

> **Challenge:** Adapter me ek click listener interface add karo (`OnItemClickListener`) taaki har row pe click hone par uska `meterId` wapas Fragment ko mile — ye exact wahi interface pattern hai jo Day 1 ke `SyncListener` jaisa tha.

### 🔬 Hands-On Lab: Recycling Apni Aankhon Se Dekho

1. `onCreateViewHolder()` aur `onBindViewHolder()` — dono ke andar ek `Log.d("Recycler", "onCreateViewHolder called")` / `Log.d("Recycler", "onBindViewHolder pos=" + position)` daalo.
2. `readings` list me **50+ dummy items** add karo (loop se generate kar sakte ho: `for (int i = 0; i < 50; i++) readings.add(new MeterReading("MTR-" + i, i * 10, "now"));`).
3. App run karo, list ko fast scroll karo, aur Logcat dekho:
   - `onCreateViewHolder` sirf **10-15 baar** chalega total (screen pe jitne items fit hote hain, thoda buffer).
   - `onBindViewHolder` **har scroll pe baar-baar** chalega — ye recycling live dikh rahi hai!

> **Yaad Rakho:** Agar tumhe `onCreateViewHolder` bhi baar-baar chalte dikhe (jaise har scroll pe), iska matlab recycling sahi se kaam nahi kar rahi — kuch galat setup hai (jaise har baar naya Adapter banana galti se).

## 📋 Quick Revision

| Concept | One-liner |
|---------|-----------|
| RecyclerView | Views recycle karta hai, `ListView` se fast |
| Adapter | Data ko views se jodne wala bridge |
| ViewHolder | Ek row ke views ko hold karta hai — repeat `findViewById` avoid |
| onCreateViewHolder | Naya view banata hai (rare, mehnga) |
| onBindViewHolder | Data set karta hai (frequent, sasta — heavy work mat karo) |
| getItemCount | List ka total size |
| Multiple View Types | `getItemViewType()` se decide, alag ViewHolder subclasses |
| notifyItemInserted/Removed | `notifyDataSetChanged()` se fast, specific update |
| Fragment | Activity ke andar reusable UI piece |
| Fragment Lifecycle | Activity se zyada steps — `onAttach`→...→`onDetach` |
| Activity vs Fragment | Poora context switch = Activity; same screen ke andar content badle = Fragment |
| Fragment Navigation | `FragmentManager.replace()` + `addToBackStack()` |

## 🎯 Interview Tips

1. **Q: `ListView` ke bajaye `RecyclerView` kyun?**
   *A: View recycling built-in hai, ViewHolder pattern enforce karta hai, aur LayoutManager (Linear/Grid/Staggered) flexible hai.*

2. **Q: `onBindViewHolder` me heavy kaam kyun nahi karna chahiye?**
   *A: Ye scroll ke har frame pe multiple baar chal sakta hai — heavy kaam UI ko janky/laggy bana dega.*

3. **Q: `onDestroyView()` me binding ko `null` kyun karte hain?**
   *A: Fragment ka view destroy ho sakta hai jabki Fragment instance zinda rahe (back stack me) — purana view reference memory leak karega.*

4. **Q: Kab Activity, kab Fragment use karoge?**
   *A: Poora naya context/flow (login, onboarding) → Activity. Same screen ke andar switching content (tabs, list-detail) → Fragment.*
