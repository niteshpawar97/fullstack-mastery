## Block 1 — Smart Meter Data Flow

### Real-World Data Flow

```
[Smart Meter Device] → [Meter Reading (Field Worker App)] → [Local Room DB]
                                                                    ↓
                                                          [Background Sync — WorkManager]
                                                                    ↓
                                                              [Server API]
```

```java
@Entity(tableName = "meter_readings")
public class MeterReadingEntity {
    @PrimaryKey(autoGenerate = true)
    public int id;

    @ColumnInfo(name = "meter_id")
    public String meterId;          // konsa meter (device identity)

    @ColumnInfo(name = "customer_id")
    public String customerId;       // kiska meter hai

    public double reading;          // current unit reading
    public long timestamp;          // kab li gayi reading (epoch millis)

    @ColumnInfo(name = "sync_status")
    public String syncStatus;       // PENDING / SYNCED / FAILED
}
```

> **Yaad Rakho:** `Meter ID` / `Device ID` **hamesha unique** hona chahiye — real-world me har physical smart meter ka apna serial number hota hai, wahi identity hai. Do meters ka same ID hona data corruption ka sabse bada karan hai.

### Timestamp — Kyun `long` Aur Kyun Zaroori

```java
long now = System.currentTimeMillis();   // epoch milliseconds, timezone-independent
```

> **Warning:** Reading ka time device ke local `Date` object me store mat karo — timezone badalte hi comparisons galat ho jaate hain. Hamesha **epoch millis (`long`)** store karo, display ke waqt hi human-readable format me convert karo.

## Block 2 — Offline Data vs Online Data + Network Connectivity

### Network Connectivity Check

```java
public class NetworkUtils {
    public static boolean isOnline(Context context) {
        ConnectivityManager cm = (ConnectivityManager)
                context.getSystemService(Context.CONNECTIVITY_SERVICE);
        Network network = cm.getActiveNetwork();
        if (network == null) return false;

        NetworkCapabilities capabilities = cm.getNetworkCapabilities(network);
        return capabilities != null &&
               (capabilities.hasTransport(NetworkCapabilities.TRANSPORT_WIFI) ||
                capabilities.hasTransport(NetworkCapabilities.TRANSPORT_CELLULAR));
    }
}
```

### Live Network Changes Sunna

```java
ConnectivityManager.NetworkCallback networkCallback = new ConnectivityManager.NetworkCallback() {
    @Override
    public void onAvailable(@NonNull Network network) {
        // internet wapas aaya — pending readings sync karo
        triggerSync();
    }
    @Override
    public void onLost(@NonNull Network network) {
        // internet gaya — UI me offline indicator dikhao
        showOfflineBanner();
    }
};
cm.registerDefaultNetworkCallback(networkCallback);
```

> **Socho Aise:** `NetworkCallback` ek doorbell hai jo khud bajti hai jab internet aaye ya jaaye — tumhe baar-baar poochte rehne ki (polling) zaroorat nahi.

## Block 3 — Offline-First Architecture + Local Caching

### Offline-First Ka Matlab

> **Yaad Rakho:** Offline-first architecture me **Room (local DB) hamesha "source of truth" hai** — app kabhi seedhe server se UI nahi banata. Server sirf Room ko update karne ka zariya hai.

```
User Action (meter reading save karta hai)
        ↓
   Room me turant save (status = PENDING) — UI turant update, internet ho ya na ho
        ↓
   Background me sync attempt (agar online hai)
        ↓
   Success → status = SYNCED   |   Fail → status = FAILED (retry later)
```

```java
public class MeterRepository {
    private final MeterReadingDao dao;
    private final MeterApiService api;

    public void saveReading(String meterId, double reading) {
        MeterReadingEntity entity = new MeterReadingEntity();
        entity.meterId = meterId;
        entity.reading = reading;
        entity.timestamp = System.currentTimeMillis();
        entity.syncStatus = "PENDING";

        executor.execute(() -> {
            dao.insert(entity);           // turant local save — offline bhi kaam karta hai
            attemptSync(entity);          // agar online hai to turant sync try karo
        });
    }
}
```

> **Socho Aise:** Offline-first app ek diary jaisa hai — pehle diary (Room) me likhte ho chahe internet ho ya na ho, baad me fursat se (background sync) office (server) ko report bhej dete ho. Diary hamesha up-to-date rehti hai, chahe report bheji ja paayi ho ya nahi.

### Local Caching — Server Ka Data Bhi Room Me

```java
public void refreshFromServer() {
    if (!NetworkUtils.isOnline(context)) return;   // offline — kuch mat karo, local data already available hai

                executor.execute(() -> cacheServerData(res.body()));   // server data ko Room me cache karo
            }
        }
        // ...
    });
}
```

## Block 4 — Sync Status (Pending/Success/Failed) + Retry Mechanism

### Sync Status States

```java
public class SyncStatus {
    public static final String PENDING = "PENDING";   // abhi tak server ko nahi bheja
    public static final String SYNCED = "SYNCED";      // server ne confirm kar diya
    public static final String FAILED = "FAILED";      // sync try hua, fail ho gaya
}
```

```
PENDING ──(sync attempt success)──> SYNCED
PENDING ──(sync attempt fail)─────> FAILED
FAILED  ──(retry success)─────────> SYNCED
FAILED  ──(retry fail again)──────> FAILED (retry count badhta hai)
```

> **Socho Aise:** Ye bilkul courier tracking jaisa hai — "Order Placed" (PENDING) → "Out for Delivery" (syncing) → "Delivered" (SYNCED) ya "Delivery Failed, Retrying" (FAILED).

### Retry Mechanism — Exponential Backoff

```java
public void attemptSync(MeterReadingEntity entity) {
    api.submitReading(toRequest(entity)).enqueue(new Callback<MeterReadingResponse>() {
        @Override
        public void onResponse(Call<MeterReadingResponse> call, Response<MeterReadingResponse> response) {
            if (response.isSuccessful()) {
                entity.syncStatus = SyncStatus.SYNCED;
            } else {
                entity.syncStatus = SyncStatus.FAILED;
            }
            executor.execute(() -> dao.update(entity));
        }
        @Override
        public void onFailure(Call<MeterReadingResponse> call, Throwable t) {
            entity.syncStatus = SyncStatus.FAILED;
            executor.execute(() -> dao.update(entity));
        }
    });
}
```

> **Tip:** Har retry ke beech **same interval** rakhne ke bajaye (jaise har 5 sec), **exponential backoff** use karo — 1st retry 10 sec baad, 2nd 30 sec baad, 3rd 2 min baad. Isse server pe unnecessary load nahi aata jab wo already down ho.

> **Yaad Rakho:** WorkManager (Block 7) **built-in exponential backoff support** deta hai — khud implement karne ki zaroorat nahi padegi.

## Block 5 — Duplicate Prevention + Data Consistency

### Duplicate Prevention Ka Problem

> **Interview Trap:** "Agar sync request server tak pahunch gayi aur record save ho gaya, par response wapas aate waqt network cut gaya — app ko lagega FAILED, wo dobara try karega — ab server pe **duplicate record** ban jaayega."

### Solution: Idempotency Key (Client-Generated Unique ID)

```java
@Entity(tableName = "meter_readings")
public class MeterReadingEntity {
    @PrimaryKey(autoGenerate = true)
    public int id;

    @ColumnInfo(name = "client_uuid")
    public String clientUuid;   // client-side generated, server duplicate check ke liye use karta hai

    // ... baaki fields
}
```

```java
entity.clientUuid = UUID.randomUUID().toString();   // save karte waqt hi generate karo, resend pe same rahega
```

```json
POST /api/readings
{
  "clientUuid": "a1b2c3d4-...",
  "meterId": "MTR-001",
  "reading": 245.5
}
```

Server side: agar `clientUuid` already database me exist karta hai, to naya record **nahi banega** — purana wahi return kar dega ("already processed").

> **Socho Aise:** `clientUuid` ek unique token number hai jo tum lene se pehle hi le lete ho — chahe counter pe request 5 baar bhi pahunche, token number same rehne se sirf **ek hi** order process hoga.

### Data Consistency

```java
// Sync se pehle, purana status check karo — SYNCED ko dobara mat bhejo
public void syncPendingReadings() {
    List<MeterReadingEntity> pending = dao.getReadingsByStatus(SyncStatus.PENDING);
    List<MeterReadingEntity> failed = dao.getReadingsByStatus(SyncStatus.FAILED);

    for (MeterReadingEntity entity : pending) attemptSync(entity);
    for (MeterReadingEntity entity : failed) attemptSync(entity);
    // SYNCED wale kabhi dobara nahi bheje jaate
}
```

> **Yaad Rakho:** Data consistency ka matlab hai — local (Room) aur remote (Server) state **kabhi contradict** na karein. `SYNCED` record ko dobara sync attempt karna waste hai aur duplicate risk badhata hai.

## Block 6 — Batch Sync, Pagination, Large Dataset

### Batch Sync — Ek-Ek Nahi, Group Me Bhejo

```java
public interface MeterApiService {
    @POST("readings/batch")
    Call<BatchSyncResponse> submitBatch(@Body List<MeterReadingRequest> readings);
}

public void syncInBatches() {
    List<MeterReadingEntity> pending = dao.getReadingsByStatus(SyncStatus.PENDING);
    int batchSize = 20;

    for (int i = 0; i < pending.size(); i += batchSize) {
        List<MeterReadingEntity> batch = pending.subList(i, Math.min(i + batchSize, pending.size()));
        api.submitBatch(toRequestList(batch)).enqueue(/* handle response */);
    }
}
```

> **Socho Aise:** 100 chitthiyan post karni hain — 100 baar post office jaana (one-by-one API calls) ke bajaye, ek hi baar 100 chitthiyon ka bundle (batch) le jaana — bahut kam network overhead.

```java
        LinearLayoutManager lm = (LinearLayoutManager) rv.getLayoutManager();
```

## Block 7 — WorkManager: Background Sync

### WorkManager Kyun

`WorkManager` **guaranteed background execution** deta hai — app band ho jaaye, phone restart ho jaaye, phir bhi scheduled kaam ek din chalega jab constraints (jaise internet) satisfy ho jaayenge.

```groovy
implementation 'androidx.work:work-runtime:2.9.0'
```

### Worker Class Banao

```java
public class SyncWorker extends Worker {
    public SyncWorker(@NonNull Context context, @NonNull WorkerParameters params) {
        super(context, params);
    }

    @NonNull
    @Override
    public Result doWork() {
        MeterRepository repository = new MeterRepository(getApplicationContext());
        boolean success = repository.syncPendingReadingsBlocking();   // synchronous version yahan

        if (success) {
            showNotification("Sync Complete", "All readings synced successfully");
            return Result.success();
        } else {
            showNotification("Sync Failed", "Will retry automatically");
            return Result.retry();   // WorkManager khud exponential backoff se retry karega
        }
    }
}
```

### Work Request Schedule Karna

```java
Constraints constraints = new Constraints.Builder()
        .setRequiredNetworkType(NetworkType.CONNECTED)   // sirf internet available hone pe chale
        .build();

PeriodicWorkRequest syncRequest = new PeriodicWorkRequest.Builder(SyncWorker.class, 15, TimeUnit.MINUTES)
        .setConstraints(constraints)
        .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 10, TimeUnit.SECONDS)
        .build();

WorkManager.getInstance(context)
        .enqueueUniquePeriodicWork("meter_sync", ExistingPeriodicWorkPolicy.KEEP, syncRequest);
```

> **Socho Aise:** `WorkManager` ek bahut zimmedaar assistant hai — tum use bol dete ho "jab bhi internet mile, ye kaam kar dena" — chahe tum so jao (app closed) ya phone restart ho jaaye, wo apna kaam yaad rakhta hai aur pura karta hai.

> **Yaad Rakho:** `PeriodicWorkRequest` ka **minimum interval 15 minutes** hai — isse kam frequent schedule nahi kar sakte (battery saving ke liye Android ki hard limit hai). Turant sync ke liye (jaise user manually "Sync Now" dabaye) `OneTimeWorkRequest` use karo.

```java
OneTimeWorkRequest immediateSync = new OneTimeWorkRequest.Builder(SyncWorker.class)
        .setConstraints(constraints)
        .build();
WorkManager.getInstance(context).enqueue(immediateSync);
```

## Block 8 — Mini Project: Full Offline-Sync Flow

Sab kuch combine — ek button "Save Reading" jo:
1. Room me turant save kare (status PENDING)
2. Agar online hai, turant sync try kare
3. Agar offline hai, WorkManager schedule kare taaki internet aane pe automatic sync ho

```java
public class ReadingRepository {
    public void saveAndSync(String meterId, double reading, Context context) {
        MeterReadingEntity entity = new MeterReadingEntity();
        entity.meterId = meterId;
        entity.reading = reading;
        entity.timestamp = System.currentTimeMillis();
        entity.clientUuid = UUID.randomUUID().toString();
        entity.syncStatus = SyncStatus.PENDING;

        executor.execute(() -> {
            dao.insert(entity);   // turant local save — UI ko turant dikh jaayega

            if (NetworkUtils.isOnline(context)) {
                attemptSync(entity);   // turant try karo
            } else {
                scheduleBackgroundSync(context);   // baad me WorkManager sambhalega
            }
        });
    }

    private void scheduleBackgroundSync(Context context) {
        Constraints constraints = new Constraints.Builder()
                .setRequiredNetworkType(NetworkType.CONNECTED)
                .build();
        OneTimeWorkRequest request = new OneTimeWorkRequest.Builder(SyncWorker.class)
                .setConstraints(constraints)
                .build();
        WorkManager.getInstance(context).enqueue(request);
    }
}
```

## 🎯 Interview Tips

1. **Q: Offline-first architecture kaise design karoge?**
   *A: Room ko source of truth banao — UI hamesha Room se padhe. Retrofit background me Room ko update karta hai. Is se app internet ke bina bhi fully functional rehta hai.*

2. **Q: Duplicate sync kaise rokoge agar response network me hi kho jaaye?**
   *A: Client-side generated unique ID (`clientUuid`/idempotency key) bhejo — server usse duplicate check karke same record dobara nahi banayega.*

3. **Q: `WorkManager` kyun, `Thread` ya `AlarmManager` kyun nahi?**
   *A: WorkManager app-closed aur device-restart survive karta hai, constraints (network, battery) respect karta hai, aur automatic retry/backoff deta hai — ye sab manually implement karna error-prone hai.*

4. **Q: Large dataset ko RecyclerView me kaise handle karoge?**
   *A: Pagination — server se chhote pages me data lao, scroll-end detect karke next page load karo. Ek saath sab kuch load karna memory issues deta hai.*
