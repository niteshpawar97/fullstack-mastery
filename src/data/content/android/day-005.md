## Block 1 — Authentication vs Authorization + Login Flow

### Authentication vs Authorization

| | Authentication | Authorization |
|---|---|---|
| Sawaal | "Tum kaun ho?" | "Tumhe ye karne ki permission hai?" |
| Example | Login (email + password) | Admin sirf meters delete kar sakta hai, normal user nahi |
| Fail hone pe | `401 Unauthorized` | `403 Forbidden` |

> **Socho Aise:** Society ke gate pe guard tumhara ID card check karta hai (**Authentication** — "tum resident ho"). Ander jaake, tumhare paas sirf apne flat ki chaabi hai, neighbour ke flat ki nahi (**Authorization** — "tumhe ye specific cheez access karne ki permission hai").

### 🧠 Theory: Password Server Pe Kaise Store Hota Hai (Plain Text Kabhi Nahi)

App password ko server ko bhejti hai (HTTPS ke andar encrypted), par server us password ko **kabhi bhi as-it-is database me save nahi karta**. Agar kare aur database leak ho jaaye, saare users ke real passwords expose ho jaayenge.

Iske bajaye server **hashing** karta hai — password ko ek **one-way mathematical function** (jaise bcrypt) se guzarta hai jo ek fixed-length, irreversible string banati hai:

```
"mypassword123"  ──(bcrypt hash)──>  "$2b$10$N9qo8uLOickgx2ZMRZoMy..."
```

Login ke waqt, tumne jo password diya wo **dobara hash** karke, database me saved hash se compare hota hai — match ho to login success. Original password kabhi kahin store nahi hota, na hi wapas nikala ja sakta hai.

> **Yaad Rakho:** "Hashing" aur "Encryption" alag hain — Encryption **reversible** hai (decrypt kar sakte ho, chaabi se), Hashing **one-way** hai (kabhi bhi original wapas nahi nikalta). Passwords hamesha **hash** hote hain, encrypt nahi.

> **Tip (Android side):** Ye sab kaam **server pe** hota hai, Android app ko bcrypt implement karne ki zaroorat nahi — app sirf plain password HTTPS ke andar securely bhejta hai, server hashing sambhalta hai.

### Full Login Flow

```
1. User email + password submit karta hai
2. App POST /login API call karti hai (credentials ke saath)
3. Server verify karta hai → agar sahi, JWT token generate karke bhejta hai
4. App token ko secure storage me save karti hai
5. Har future API call me token "Authorization" header me jaata hai
6. Server har request pe token verify karta hai — sahi hone pe hi response deta hai
```

```java
public interface AuthApiService {
    @POST("auth/login")
    Call<LoginResponse> login(@Body LoginRequest request);
}

public class LoginRequest {
    String email;
    String password;
    public LoginRequest(String email, String password) {
        this.email = email;
        this.password = password;
    }
}

public class LoginResponse {
    String token;
    String userId;
    long expiresAt;
}
```

## Block 2 — JWT: Bearer Token, Token Expiry

### JWT Kya Hai

**JWT (JSON Web Token)** teen parts ka ek string hai: `Header.Payload.Signature`

```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOiIxMDEiLCJleHAiOjE3NTU3NjY4MDB9.4f8a3c...
     HEADER                    PAYLOAD (user data)              SIGNATURE
```

> **Socho Aise:** JWT ek sealed, signed letter jaisa hai — payload (user info) readable hai (base64, encrypted nahi!), par signature prove karta hai ki letter server ne hi likha hai aur beech me kisi ne badla nahi.

> **Warning:** JWT payload **encrypted nahi hota**, sirf **encoded** hota hai — koi bhi decode karke padh sakta hai. Isiliye password ya sensitive data JWT payload me kabhi mat daalo, sirf userId, role jaisi non-sensitive info.

### Bearer Token — Header Me Kaise Bhejte Hain

```
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOiIxMDEifQ...
```

```java
Call<MeterReadingResponse> call = api.getMeter("MTR-001");
// Header manually add karna (interceptor se automate karenge Block 3 me)
```

### Token Expiry

```java
public boolean isTokenExpired(long expiresAt) {
    return System.currentTimeMillis() > expiresAt;
}

if (isTokenExpired(loginResponse.expiresAt)) {
    // user ko dobara login karwao, ya refresh token flow chalao
    redirectToLogin();
}
```

> **Yaad Rakho:** Token **hamesha ke liye valid nahi** hota — security ke liye expiry time hota hai (e.g., 1 hour, 7 din). Expire hone pe app ko dobara login karwana ya "refresh token" se naya token lena padta hai.

## Block 3 — Secure Storage: Android Keystore + SharedPreferences

### SharedPreferences — Simple Key-Value Storage

```java
SharedPreferences prefs = getSharedPreferences("app_prefs", MODE_PRIVATE);
SharedPreferences.Editor editor = prefs.edit();
editor.putString("user_name", "Ashutosh");
editor.putBoolean("is_logged_in", true);
editor.apply();

String name = prefs.getString("user_name", "");
boolean isLoggedIn = prefs.getBoolean("is_logged_in", false);
```

> **Warning:** Normal `SharedPreferences` **plain text** me store hoti hai device ke andar (rooted phone pe padhi ja sakti hai). JWT token jaisi sensitive cheez ke liye ye **kaafi nahi** hai.

### EncryptedSharedPreferences — JWT Token Ke Liye

```groovy
implementation 'androidx.security:security-crypto:1.1.0-alpha06'
```

```java
MasterKey masterKey = new MasterKey.Builder(context)
        .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
        .build();

SharedPreferences securePrefs = EncryptedSharedPreferences.create(
        context,
        "secure_prefs",
        masterKey,
        EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
        EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
);

securePrefs.edit().putString("jwt_token", token).apply();
String savedToken = securePrefs.getString("jwt_token", null);
```

> **Socho Aise:** `EncryptedSharedPreferences` ek locker hai jiski chaabi khud device ke **Android Keystore** (hardware-backed secure area) me rehti hai — chaabi bhi kisi ko dikhti nahi, isiliye locker ka contents bhi safe rehta hai.

### Android Keystore

Android Keystore ek **hardware-backed secure storage** hai jahan encryption keys generate/store hoti hain — keys khud kabhi app code me expose nahi hoti, sirf "use karo" bola jaata hai. `EncryptedSharedPreferences` andar hi andar Keystore use karta hai.

| Storage | Use Case |
|---------|----------|
| `SharedPreferences` | Non-sensitive settings — theme, language, onboarding-seen flag |
| `EncryptedSharedPreferences` | JWT tokens, refresh tokens, sensitive user data |
| `Android Keystore` (direct) | Encryption keys khud generate/manage karna (advanced use case) |

## Block 4 — SQLite Background + Room Kyun

### SQLite — Android Ka Built-in Database Engine

Har Android device ke andar **SQLite** already hota hai — ek lightweight relational database. Directly use karna verbose hai (raw SQL strings, manual cursor management, crash-prone).

```java
// Raw SQLite — verbose aur error-prone (isliye Room use karte hain)
SQLiteDatabase db = ...;
Cursor cursor = db.rawQuery("SELECT * FROM readings WHERE meter_id = ?", new String[]{"MTR-001"});
```

### Room — SQLite Ke Upar Type-Safe Layer

**Room** Google ka official library hai jo SQLite ko **compile-time verified**, type-safe Java objects ke through use karne deti hai.

```groovy
implementation 'androidx.room:room-runtime:2.6.1'
annotationProcessor 'androidx.room:room-compiler:2.6.1'
```

> **Socho Aise:** Raw SQLite = haath se gaadi chalana (clutch, gear sab manual, mistake ki gunjaish). Room = automatic gaadi — same engine (SQLite) ke upar, par safer aur aasan controls.

| | Raw SQLite | Room |
|---|---|---|
| Queries | Raw SQL strings | Annotations (`@Query`) — compile-time check |
| Error catching | Runtime crash | Compile-time error |
| Boilerplate | Bahut zyada | Kam — auto-generated code |

## Block 5 — Room: Entity, DAO, Database

### Entity — Table Ka Blueprint

```java
@Entity(tableName = "meter_readings")
public class MeterReadingEntity {
    @PrimaryKey(autoGenerate = true)
    public int id;

    @ColumnInfo(name = "meter_id")
    public String meterId;

    public double reading;
    public long timestamp;
}
```

> **Yaad Rakho:** `@Entity` = ek table. Har field ek column banta hai. `@PrimaryKey(autoGenerate = true)` matlab Room khud unique ID assign karega.

### DAO (Data Access Object) — Queries Ka Interface

```java
@Dao
public interface MeterReadingDao {

    @Insert
    void insert(MeterReadingEntity reading);

    @Query("SELECT * FROM meter_readings WHERE meter_id = :meterId ORDER BY timestamp DESC")
    List<MeterReadingEntity> getReadingsForMeter(String meterId);

    @Query("SELECT * FROM meter_readings")
    List<MeterReadingEntity> getAllReadings();

    @Update
    void update(MeterReadingEntity reading);

    @Delete
    void delete(MeterReadingEntity reading);
}
```

> **Socho Aise:** `DAO` ek waiter hai — tum usse "SELECT * jaisi order" bolte ho, wo kitchen (database) se laake deta hai. Tumhe kabhi kitchen (raw SQL cursor management) ke andar jaane ki zaroorat nahi.

### Database — Sab Kuch Jodne Wali Class

```java
@Database(entities = {MeterReadingEntity.class}, version = 1)
public abstract class AppDatabase extends RoomDatabase {
    public abstract MeterReadingDao meterReadingDao();

    private static volatile AppDatabase INSTANCE;

    public static AppDatabase getInstance(Context context) {
        if (INSTANCE == null) {
            synchronized (AppDatabase.class) {
                if (INSTANCE == null) {
                    INSTANCE = Room.databaseBuilder(context.getApplicationContext(),
                                    AppDatabase.class, "meter_database")
                            .build();
                }
            }
        }
        return INSTANCE;
    }
}
```

> **Warning:** `AppDatabase` **singleton** honi chahiye — multiple instances banane se data corruption aur memory waste ho sakti hai. `synchronized` block isliye hai taaki multi-threaded access safe rahe.

## Block 6 — CRUD Operations with Room

```java
AppDatabase db = AppDatabase.getInstance(context);
MeterReadingDao dao = db.meterReadingDao();

// CREATE
MeterReadingEntity newReading = new MeterReadingEntity();
newReading.meterId = "MTR-001";
newReading.reading = 245.5;
newReading.timestamp = System.currentTimeMillis();
dao.insert(newReading);

// READ
List<MeterReadingEntity> readings = dao.getReadingsForMeter("MTR-001");

// UPDATE
newReading.reading = 260.0;
dao.update(newReading);

// DELETE
dao.delete(newReading);
```

> **Warning:** Room ke saare database operations **main thread pe disallowed** hain by default — `IllegalStateException` crash milega. Ye hamesha background thread (jaise `ExecutorService` ya Day 6 me sikhne wale `WorkManager`) me chalao.

```java
ExecutorService executor = Executors.newSingleThreadExecutor();
executor.execute(() -> {
    dao.insert(newReading);   // background thread pe safe
});
```

## Block 7 — Room + Retrofit Combine Karna

Ye **real apps ka core pattern** hai — server se data lao (Retrofit), local DB me save karo (Room), UI ko DB se hi dikhao.

```java
public class MeterRepository {
    private final MeterApiService api;
    private final MeterReadingDao dao;
    private final ExecutorService executor;

    public MeterRepository(Context context) {
        api = RetrofitClient.getInstance().create(MeterApiService.class);
        dao = AppDatabase.getInstance(context).meterReadingDao();
        executor = Executors.newSingleThreadExecutor();
    }

    public void refreshReadings(String meterId) {
        api.getReadings(meterId, 50).enqueue(new Callback<List<MeterReadingResponse>>() {
            @Override
            public void onResponse(Call<List<MeterReadingResponse>> call, Response<List<MeterReadingResponse>> response) {
                if (response.isSuccessful() && response.body() != null) {
                    executor.execute(() -> {
                        for (MeterReadingResponse r : response.body()) {
                            MeterReadingEntity entity = new MeterReadingEntity();
                            entity.meterId = r.meterId;
                            entity.reading = r.reading;
                            entity.timestamp = System.currentTimeMillis();
                            dao.insert(entity);   // server se aaya data, local DB me save
                        }
                    });
                }
            }
            @Override
            public void onFailure(Call<List<MeterReadingResponse>> call, Throwable t) {
                // network fail — koi baat nahi, purana local data already Room me hai
                Log.e("Repository", "Refresh failed, showing cached data");
            }
        });
    }

    public List<MeterReadingEntity> getCachedReadings(String meterId) {
        return dao.getReadingsForMeter(meterId);   // UI hamesha isse padhe — offline bhi kaam karega
    }
}
```

> **Socho Aise:** Room = tumhara ghar ka fridge (hamesha available, chahe bahar dukaan band ho). Retrofit = dukaan se saaman laana. Smart approach: pehle fridge (Room) se dikhao (turant, offline bhi), phir background me dukaan (server) se fresh saaman laa ke fridge update kar do.

> **Yaad Rakho:** Ye exact pattern — **UI Room se padhe, Retrofit sirf Room ko update kare** — offline-first architecture ka core hai, jo poora Day 6 isi pe based hoga.

## Block 8 — Mini Project: Login + Local Meter Storage

```java
public class AuthRepository {
    private final AuthApiService api;
    private final SharedPreferences securePrefs;

    public AuthRepository(Context context) {
        api = RetrofitClient.getInstance().create(AuthApiService.class);
        securePrefs = createSecurePrefs(context);
    }

    public void login(String email, String password, AuthCallback callback) {
        api.login(new LoginRequest(email, password)).enqueue(new Callback<LoginResponse>() {
            @Override
            public void onResponse(Call<LoginResponse> call, Response<LoginResponse> response) {
                if (response.isSuccessful() && response.body() != null) {
                    securePrefs.edit()
                            .putString("jwt_token", response.body().token)
                            .putLong("expires_at", response.body().expiresAt)
                            .apply();
                    callback.onSuccess();
                } else {
                    callback.onError("Invalid credentials");
                }
            }
            @Override
            public void onFailure(Call<LoginResponse> call, Throwable t) {
                callback.onError("Network error: " + t.getMessage());
            }
        });
    }

    public boolean isLoggedIn() {
        String token = securePrefs.getString("jwt_token", null);
        long expiresAt = securePrefs.getLong("expires_at", 0);
        return token != null && System.currentTimeMillis() < expiresAt;
    }

    public void logout() {
        securePrefs.edit().clear().apply();
    }

    public interface AuthCallback {
        void onSuccess();
        void onError(String message);
    }
}
```

> **Challenge:** `LoginActivity` banao jo `AuthRepository.login()` call kare, success pe `DashboardActivity` kholein, aur app start hone pe `isLoggedIn()` check karke direct Dashboard ya Login pe route kare (splash-screen style).

## 🎯 Interview Tips

1. **Q: JWT secure hai kya?**
   *A: Signature se tamper-proof hai, par payload encrypted nahi — sirf encoded. Sensitive data payload me mat daalo.*

2. **Q: SharedPreferences me directly token kyun nahi store karte?**
   *A: Plain text me store hoti hai — rooted device pe readable. `EncryptedSharedPreferences` (Keystore-backed) use karo.*

3. **Q: Room ki main-thread database call pe crash kyun karta hai?**
   *A: Disk I/O slow hai — main thread pe karne se UI freeze/ANR ho sakta hai, isliye Room design hi enforce karta hai background thread.*

4. **Q: Repository pattern me Room aur Retrofit dono kyun rakhte ho?**
   *A: Room = offline-first source of truth (UI isi se padhe), Retrofit = background me Room ko fresh data se update karne ka zariya.*
